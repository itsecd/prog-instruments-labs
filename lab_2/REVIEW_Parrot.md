## 1. Что делает исходный код

Программа моделирует три вида попугаев: European, African и Norwegian Blue. Метод `speed()` вычисляет скорость с учётом вида, числа кокосов, напряжения и состояния `nailed`. Метод `cry()` возвращает звук. В файле `test_parrot.py` есть тесты ожидаемого поведения для обычных значений.

Это **учебное ревью**, а не утверждение, что автор проекта допустил случайные ошибки: Kata специально предназначена для практики рефакторинга. Предложенные изменения следует внедрять с сохранением исходного поведения для допустимых входных данных и проверять тестами.

## 2. Замечания по конкретным строкам

### CR-01 — Повторение ветвления по типу (DRY / нарушение инкапсуляции поведения)
**Файл:** `Python/parrot.py`, строки **18–34**. **Приоритет:** высокий, архитектурный.

**Фрагмент:**
```python
match self._type:
    case ParrotType.EUROPEAN: ...
    case ParrotType.AFRICAN: ...
    case ParrotType.NORWEGIAN_BLUE: ...
```

**Проблема.** Один и тот же список видов повторно перечисляется в `speed()` и `cry()`. При добавлении нового вида придётся редактировать оба метода, легко пропустив один из них. Это признак *switch statements / repeated conditional logic*, связанный с нарушением принципа Open/Closed.

**Предложение.** После закрепления поведения тестами перенести логику видов в отдельные классы, реализующие общий интерфейс. Тогда выбор нужного класса происходит в одном месте, а `speed()` и `cry()` не содержат дублирующихся `match`.

```python
class EuropeanParrot:
    def speed(self) -> float:
        return 12.0

    def cry(self) -> str:
        return "Sqoork!"
```

Это иллюстрация подхода, а не полная замена всего модуля: African и Norwegian Blue также должны реализовать интерфейс и сохранить прежние расчёты.

### CR-02 — Неизвестный вид возвращает `None` без объяснения (логическая устойчивость)
**Файл:** `Python/parrot.py`, строки **18–34**. **Приоритет:** высокий.

**Проблема.** У `match` отсутствует завершающий `case _`. Если ошибочно передать, например, строку вместо `ParrotType`, `speed()` и `cry()` закончатся неявным `return None`. Такой результат может вызвать непонятную ошибку гораздо позже.

**Предложение.** Проверять тип при создании объекта или явно отвергать недопустимые значения. Если оставлять текущую структуру:

```python
case _:
    raise ValueError(f"Unsupported parrot type: {self._type!r}")
```

Добавить тест `pytest.raises(ValueError)` для неизвестного вида. Это сознательное уточнение контракта для некорректного ввода, поэтому перед внедрением согласовать ожидаемое поведение.

### CR-03 — Конструктор принимает параметры, не относящиеся к виду (Primitive Obsession / низкая связность данных)
**Файл:** `Python/parrot.py`, строки **12–16**. **Приоритет:** средний.

**Проблема.** Любой попугай обязан получить четыре параметра, хотя число кокосов нужно только African, а напряжение и `nailed` — только Norwegian Blue. Например, European создаётся как `Parrot(ParrotType.EUROPEAN, 0, 0, False)`: три значения служат заполнителями. Это допускает бессмысленные состояния.

**Предложение.** Использовать разные конструкторы/типы с осмысленными аргументами:

```python
EuropeanParrot()
AfricanParrot(number_of_coconuts=2)
NorwegianBlueParrot(voltage=1.5, nailed=False)
```

Альтернатива без немедленной смены API — фабричные функции с валидацией соответствия параметров виду.

### CR-04 — Нет явной валидации входных значений (устойчивость / инварианты)
**Файл:** `Python/parrot.py`, строки **12–16, 22–25, 34**. **Приоритет:** средний.

**Проблема.** Конструктор не проверяет, что кокосы — неотрицательное целое число, напряжение — конечное число, а `nailed` — логический флаг. Например, отрицательное число кокосов увеличит расчётную скорость африканского попугая (`12 - 9 * (-1) = 21`) — сомнительный сценарий для предметной области. В текущих тестах такого случая нет.

**Предложение.** Сформулировать инварианты модели и проверять значения на входе:

```python
if not isinstance(number_of_coconuts, int) or number_of_coconuts < 0:
    raise ValueError("number_of_coconuts must be a non-negative integer")
```

При добавлении проверки учитывать, что `bool` в Python является подклассом `int`: для строгого контракта предпочтительно `type(value) is int`. Для напряжения отдельно определить допустимый диапазон и обработку NaN/Infinity. Это рекомендация по усилению контракта, а не доказанная ошибка для допустимого входа.

### CR-05 — «Магические числа» и неочевидная роль констант (читаемость / поддерживаемость)
**Файл:** `Python/parrot.py`, строки **23, 37, 40, 43**. **Приоритет:** средний.

**Проблема.** Значения `24.0`, `9.0`, `12.0` встроены непосредственно в расчёты и вспомогательные методы. Из имён `_load_factor` и `_base_speed` можно догадаться об их смысле, однако ограничение `24.0` не имеет собственного имени; при изменении предметных правил трудно найти связанную настройку.

**Предложение.** Выделить именованные константы и явно отразить ограничение скорости:

```python
BASE_SPEED = 12.0
COCONUT_LOAD_FACTOR = 9.0
MAX_NORWEGIAN_SPEED = 24.0

return min(MAX_NORWEGIAN_SPEED, voltage * BASE_SPEED)
```

Если правила зависят от конкретного вида, хранить константы в соответствующем классе, а не делать глобальные настройки всего проекта.

### CR-06 — Лишнее создание списка в `min` (эффективность / читаемость)
**Файл:** `Python/parrot.py`, строка **37**. **Приоритет:** низкий.

**Исходный фрагмент:**
```python
return min([24.0, voltage * self._base_speed()])
```

**Проблема.** Для сравнения двух аргументов создаётся временный список. Это незначительные накладные расходы, но усложняет запись без пользы.

**Предложение:**
```python
return min(24.0, voltage * self._base_speed())
```

Поведение для обычных числовых значений не меняется.

### CR-07 — Нет аннотаций типов и документированного контракта (поддерживаемость)
**Файл:** `Python/parrot.py`, строки **12, 18, 27, 36, 39, 42**. **Приоритет:** средний.

**Проблема.** Из сигнатур нельзя понять допустимые типы и тип результата без чтения реализации. Для метода `speed()` ожидается число, а `cry()` должен вернуть строку, но это не отражено в API.

**Предложение.** Добавить типы и краткие docstrings, например:

```python
def speed(self) -> float:
    """Return flight speed for this parrot, in model units."""
```

Конструктор можно объявить с `type_of_parrot: ParrotType`, `number_of_coconuts: int`, `voltage: float`, `nailed: bool`; `__init__` возвращает `None`. Аннотации не заменяют runtime-валидацию из CR-04.

### CR-08 — Несоответствие между `speed()` и `cry()` для прибитого Norwegian Blue (доменная неоднозначность)
**Файл:** `Python/parrot.py`, строки **24–25, 33–34**. **Приоритет:** средний, требует уточнения требований.

**Проблема.** Для `NORWEGIAN_BLUE` признак `nailed=True` принудительно обнуляет скорость, но не участвует в выборе звука: при положительном напряжении прибитый попугай всё равно возвращает `"Bzzzzzz"`. Это **не обязательно ошибка**: возможно, прибитый попугай способен издавать звук, но не летать. Правило домена в коде не объяснено.

**Предложение.** Явно описать бизнес-правило в тесте и документации. Если по требованиям звук должен зависеть от `nailed`, дополнить условие `cry()` и соответствующие тесты. Без требований поведение не изменять.

### CR-09 — Недостаточно тестов на некорректный ввод и граничные случаи (тестируемость)
**Файл:** `Python/test_parrot.py`, строки **4–56**. **Приоритет:** средний.

**Проблема.** Тесты охватывают несколько обычных сценариев, но не задают ожидаемый контракт для неизвестного вида, отрицательных кокосов, отрицательного/нулевого напряжения, неверных типов, `nailed=True` при положительном напряжении для `cry()`. Из-за этого можно непреднамеренно менять поведение на границах при рефакторинге.

**Предложение.** Дополнить тесты после согласования контракта. Например, зафиксировать поведение скорости для прибитого Norwegian Blue:

```python
def test_nailed_norwegian_blue_stays_still():
    parrot = Parrot(ParrotType.NORWEGIAN_BLUE, 0, 4, True)
    assert parrot.speed() == 0.0
```

А после реализации CR-02 добавить отдельный негативный тест для неизвестного вида. Регрессионные тесты должны предшествовать архитектурному рефакторингу.
