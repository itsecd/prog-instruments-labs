# Отчёт по лабораторной работе №7: Профайлинг и оптимизация производительности

## Описание проекта

В качестве проекта для оптимизации выбран **Currency Converter** — десктопное приложение на Python с GUI на tkinter, которое конвертирует валюты, получая актуальные курсы с сайта x-rates.com. Приложение также визуализирует результаты конвертации с помощью графика matplotlib.

---

## Найденные узкие места

С помощью встроенных средств профайлинга Python — `cProfile` (анализ CPU) и `tracemalloc` (анализ RAM) — были выявлены два критических узких места:

### Узкое место №1: Утечка памяти в отрисовке графика (RAM)

В исходном коде метод `canvasCal()` при каждом нажатии кнопки "Convert" создавал новый объект `FigureCanvasTkAgg`:

```python
def canvasCal():
    # ... получение данных ...
    scatter3 = FigureCanvasTkAgg(fig3, Frame_2ButtomL)  
    scatter3.get_tk_widget().grid(row=0, column=0)
    ax3.set_xlabel('INR')
    ax3.set_ylabel('Converted Value')
    ax3.set_title('Currency Conversion')
```

**Проблема:** Старые объекты canvas не удаляются сборщиком мусора мгновенно, что приводит к накоплению объектов в памяти и росту потребления RAM.

### Узкое место №2: Многократный парсинг HTML (CPU)

В исходном коде поиск курса валюты выполнялся через `Soup.find()` с lambda-функцией дважды за одно нажатие кнопки (в `Converted_value` и в `canvasCal`):

```python
# В Converted_value:
rate = Soup.find('table', class_='tablesorter ratesTable') \
         .find('td', text=lambda x: x == s) \
         .find_next('td').get_text()

# В canvasCal (дублирование того же поиска):
u = Soup.find('table', class_='tablesorter ratesTable') \
       .find('td', text=lambda x: x == s) \
       .find_next('td').get_text()
```

**Проблема:** Сложность поиска — O(N) по DOM-дереву, выполняется при каждом клике вместо однократного парсинга при запуске.

## Анализ производительности ДО оптимизации

### Замеры (1000 итераций симуляции нажатий кнопки)

| Метрика | Значение |
|---------|----------|
| **Время выполнения** | 208.749 секунд |
| **Пиковое использование RAM** | 9.47 MB |
| **Количество вызовов функций** | 26,900,069 |


**Ключевой вывод:** Метод `ax.clear()` потребляет **184.597 секунд из 208.749** — это **88% всего времени выполнения**. Именно он является главным узким местом по CPU.

## Анализ изменений в профиле нагрузки

### До оптимизации:
- **88% времени** тратилось на `ax.clear()` — уничтожение объектов оси
- RAM росла из-за накопления неиспользуемых `FigureCanvasTkAgg` объектов
- Парсинг HTML выполнялся 2000 раз (по 2 раза на клик)

### После оптимизации:
- `ax.clear()` полностью устранён
- RAM стабилизировалась на уровне ~1 MB
- Парсинг HTML выполняется 1 раз при запуске
- Основное время теперь тратится на `_update_ticks` (27 сек) и `_prepare_font` (21 сек) — это легитимные операции отрисовки, которые невозможно устранить без изменения визуального представления
